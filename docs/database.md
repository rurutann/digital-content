# データベース設計（ICHIE MVP）

担当：志鳥（T01） ／ 最終更新：2026-11-20

このファイルは、ICHIEのDB（PostgreSQL）とStorageの**データの形と決まりごと**をまとめたものです。
API（呼び方・入出力・エラー）は [api.md](api.md) を見てください。

---

## 1. 全体像

```
auth.users（Supabaseの匿名ユーザー。登録なしで発行される）
   │
   ├── rooms.created_by（部屋を作った人）
   ├── room_members.user_id（部屋に入った人）
   └── photos.uploader_id（写真を投稿した人）

rooms（部屋）1 ──── * room_members（入室名簿）
rooms（部屋）1 ──── * photos（写真の台帳）──── 1 Storageのファイル（写真の本体）
```

- **DBに入っているのは「記録」だけ**です。写真ファイルの本体はStorage（バケット）にあります。
- **DBの行を消しても、Storageのファイルは自動では消えません。** 削除処理（K04・K06）は両方を消します。

## 2. テーブル

### 2.1 rooms（部屋）

| 列 | 型 | 必須 | 既定値 | 説明 |
|---|---|---|---|---|
| `id` | uuid | ○ | `gen_random_uuid()` | 部屋の番号。**URLにそのまま使う**（推測されにくいランダム値） |
| `created_by` | uuid | | | 部屋を作った匿名ユーザー（`auth.users.id`）。MVPでは記録のみ（Phase 2の手動削除用） |
| `created_at` | timestamptz | ○ | `now()` | 作成日時 |
| `expires_at` | timestamptz | ○ | `now() + 24時間` | 閉まる時刻。**作成時にサーバーが記録する**（端末の時計は使わない） |
| `photo_count` | integer | ○ | `0` | 登録済みの写真の枚数（0〜100） |
| `total_bytes` | bigint | ○ | `0` | 登録済みの元の写真の合計バイト数（0〜500,000,000） |

- `photo_count`・`total_bytes` は、**写真の登録時に増やし（K05）、削除時に減らします（K04）。** 増減は台帳の登録・削除と同じトランザクションの中で、部屋の行をロックしてから行います（同時に投稿しても数がずれないようにするため）。
- DBの制約でも上限を超えられないようにしてあります（上限の判定とエラーの返し方はK05）。

### 2.2 room_members（入室名簿）

| 列 | 型 | 必須 | 既定値 | 説明 |
|---|---|---|---|---|
| `room_id` | uuid | ○ | | どの部屋か（`rooms.id`） |
| `user_id` | uuid | ○ | | 誰か（`auth.users.id`） |
| `joined_at` | timestamptz | ○ | `now()` | 最初に入った日時 |

- 主キーは `(room_id, user_id)`。**同じ人が何度参加しても1行だけ**です（2回目以降は何もしない）。
- **部屋を作った人は、作成と同時に名簿へ登録**します（create-room の中で行う）。
- 参加者の登録は join-room（Edge Function）だけが行います。端末から直接は書き込めません。

### 2.3 photos（写真の台帳）

| 列 | 型 | 必須 | 既定値 | 説明 |
|---|---|---|---|---|
| `id` | uuid | ○ | `gen_random_uuid()` | 写真の番号。**投稿する端末が `crypto.randomUUID()` で作り、Storageのパスにも使う** |
| `room_id` | uuid | ○ | | どの部屋の写真か（`rooms.id`） |
| `uploader_id` | uuid | | | 投稿した匿名ユーザー。「自分の写真か」の判定に使う |
| `storage_path` | text | ○ | | 元の写真のStorageでの置き場所（下の「3. Storage」を参照）。重複不可 |
| `thumbnail_path` | text | | | 一覧用の縮小画像の置き場所。**サーバーが登録時に作る**。作成前・失敗時は null（その場合は元の写真を表示する） |
| `mime_type` | text | ○ | | 形式。`image/jpeg`・`image/png`（HEICは投稿前に端末でJPEGへ変換するため、ここには入らない） |
| `size_bytes` | bigint | ○ | | ファイルのサイズ（バイト）。1〜20,000,000 |
| `created_at` | timestamptz | ○ | `now()` | 登録日時。一覧はこの順に並べる |

- **台帳に載るのは「登録が完了した写真」だけ**です（2段階方式。api.mdの「写真を投稿する」参照）。そのため「アップロード中」などの状態を表す列はありません。
- 写真台帳への書き込みは、Edge Function（upload-photo・delete-photo）だけが行います。

### 2.4 削除の連動

| 消すもの | 一緒に消えるもの |
|---|---|
| rooms の行 | その部屋の room_members・photos の行（`on delete cascade`） |
| auth.users の行 | room_members の行。rooms.created_by・photos.uploader_id は空（null）になる |

Storageのファイルは連動しません。**自動削除（K06）は「Storageのファイル → DBの行」の順に消します。**

## 3. Storage

| 項目 | 決まりごと |
|---|---|
| バケット | 非公開（バケット名・ポリシーはK02で決定し、[storage.md](storage.md)に記録） |
| パス（元の写真） | **`{room_id}/{photo_id}.{拡張子}`**（例：`3f9a…/8b1e….jpg`）。拡張子は `jpg` または `png` |
| パス（縮小画像） | 同じ部屋のフォルダに置く（ファイル名・縮小後の大きさはK02で決定） |
| 送り方 | **端末から supabase-js で直接送る。** Storageのポリシーで「参加者だけが自分の部屋のフォルダに送れる・読める」ようにする（参加判定はT04の関数を使う。K02） |
| 1ファイルの上限 | **20,000,000バイト（20MB）**。バケットにも同じ上限を設定する |
| 形式 | **JPEG・PNGのみ**。HEICは投稿前に端末側でJPEGへ変換する（A02） |

- 部屋ごとのフォルダなので、自動削除では `{room_id}/` のフォルダごと消します。登録されずに残ったファイルもここで片付きます。

## 4. 決まりごと（全員が同じ基準で判定する）

### 4.1 期限

- 部屋が使えるのは **`now() <= expires_at` の間**です。
- **`now() > expires_at` になったら期限切れ**です（閉まる時刻ちょうどまでは使える）。
- 判定はサーバーの時刻（DBの `now()`）で行います。RLS（T05）・Edge Function・自動削除（K06）で、この条件を共通で使ってください。

### 4.2 上限（1部屋あたり）

| 項目 | 上限 | 備考 |
|---|---|---|
| 写真の枚数 | 100枚 | |
| 合計サイズ | **500,000,000バイト** | 1MB＝1,000,000バイトとして計算 |
| 1枚のサイズ | 20,000,000バイト | |

上限の確認は、サーバー側（K05のDB関数）で行います。端末側の確認は、早めにエラーを出すための補助です。

### 4.3 書き方の統一

- テーブル名・列名は `snake_case`（例：`room_id`）。**APIのJSONも、画面側のコードも同じ名前を使います。**
- 日時は `timestamptz` で保存し、APIでは ISO 8601（UTC）の文字列で渡します。
- サイズはバイト単位の整数です。

## 5. 権限（RLS）の担当

すべてのテーブルでRLSを有効にしています。**ポリシーがないうちは、端末からは何も読み書きできません。**

| 内容 | 担当 |
|---|---|
| 参加者だけが rooms・room_members・photos を読める | T04（志鳥） |
| 期限切れの部屋を読めなくする | T05（志鳥） |
| Storageのポリシー（参加者だけが自分の部屋のフォルダに送れる・読める） | K02（斎藤） |
| 書き込み（作成・参加・写真の登録・削除） | Edge Functionが service_role で行う。関数の中で権限を確認する |

## 6. migrationと型

- migrationは `backend/supabase/migrations/` に、`作成日時_用途.sql` の名前で追加します。**取り込み済みのファイルは修正せず、変更は新しいファイルで追加します。**
- 基本テーブル：`20261120090000_create_base_tables.sql`（T01）
- 型ファイル `frontend/src/types/database.ts` は、DBから自動生成します（手で編集しない）。
  ```
  supabase gen types typescript --local > frontend/src/types/database.ts
  ```
  ※ 2026-11-20時点では、ローカル環境（T02）が未整備のため、生成結果と同じ形で手書きしています。環境ができたら生成し直して置き換えます。
- DBを変更したら、志鳥に型の再生成を依頼してください。
