# ICHIE MVP Issue一覧（機能単位・段階版）

対象リポジトリ：rurutann/digital-content

## この一覧の読み方

- **段階（M0〜M5）ごとに、スマホで実際に動く状態を1つずつ増やす**進め方です。段階の終わりには毎回、作成から最新機能までが一通り動きます。
- **IDの番号＝その人の着手順**です。佐藤さんならS01→S02→…の順に進めます。
- 1つの機能は複数人のIssueがそろって完成します。各Issueの「**連携**」の節を、着手前に必ず読んでください。
- IDは管理用で、GitHubのIssue番号ではありません。GitHubへの登録はまだしていません。
- 各担当16ポイント、合計64ポイントです。1ポイントは作業量の相対的な目安で、時間の約束ではありません。

## 連携の基本ルール

1. **着手前に「合意すること」を相手と確認する。** 各Issueの「着手前に合意すること」を相手と話し、決まった内容は`docs/api.md`に残します（編集は志鳥さんに依頼）。口頭やチャットだけで終わらせないでください。
2. **相手を待たない。** 合意した型で仮データ・モックを作って先に進めてください。モックは自分の担当ファイルの中に置き、本物と差し替える場所を1か所にまとめます。
3. **渡すときは「使い方」を添える。** PRの説明に、呼び方・引数・戻り値・エラー・動作確認の手順を書いてください。受け取る側はそのPRを読めば使える状態にします。
4. **変更は実装する前に知らせる。** 型・props・API・DBを変えるときは、使っている人に先に伝えてください。
5. **担当外のファイルを変えたいときは依頼する。** GitHubのIssueコメントで「誰に・何を・いつまでに・なぜ」を書いて依頼してください。自分で直接編集はしません。
6. **段階の最後は4人で触る。** 15分程度、スマホでその段階の「できること」を実際に操作します。動かない部分は、次の段階に進む前に直します。
7. **半日詰まったら共有する。** 連携が原因で詰まっている場合は特に、早めに相手へ伝えてください。

## 共有ファイルの窓口

| ファイル | 窓口 | 依頼が必要になる例 |
|---|---|---|
| `frontend/package.json`・ロックファイル・Vite/TS/ESLint設定・ルートの`README.md`・`.gitignore` | 佐藤 | ライブラリの追加（JSZipなど） |
| `docs/api.md`・`docs/database.md`・`frontend/src/types/database.ts` | 志鳥 | API・DB仕様の追加や変更、生成型の再生成 |
| `backend/supabase/config.toml`・`seed.sql`・`functions/_shared/`・`frontend/.env.example` | 志鳥 | 共通の認証・エラー処理、環境変数の追加 |
| migration（基本テーブル・RLS） | 志鳥 | テーブルや列の追加 |
| migration（Storage・容量・Cron）・`docs/storage.md` | 斎藤 | Storageパスや容量管理の変更 |

- **migration**：ファイル名は「作成日時＋用途」にします。取り込み済みのファイルは修正せず、変更は新しいファイルで追加します。斎藤さんのmigrationが志鳥さんのテーブルを参照する場合は、志鳥さんのmigrationが先にmainに入っていることを確認してください。
- **生成型**：DBを変更したら、志鳥さんに型の再生成を依頼してください。
- **依存関係のインストール**：ロックファイルを変えないよう、`npm install`ではなく`npm ci`を使ってください。

## Git・PRの運用

- ブランチは`feature/<ID>-<内容>`とします（例：`feature/S02-invite`）。
- PRは小さく分けて出します。作業前とPR前に、mainの更新を取り込んでください。
- PRの説明には、IssueのID・使い方・確認手順を書いてください。連携相手にはレビューを依頼します。
