# K01：画像形式の調査・MVP表示方針

更新：2026年11月13日。対象：[K01](issues/K01.md)。

## 現状と結論

文献調査と実機検証用ページの準備を実施した。**iPhone・Androidの実機検証、実投稿、写真原本の容量測定は未実施であり、K01は未完了**。この環境には検証用のJPEG・HEIC原本がなく、企画書のPNG画像のみがある。関係者への外部連絡も未実施。この文書を仕様相談・PRで共有する。

MVPの推奨方針は「ブラウザのファイル選択で受け取ったバイト列を再圧縮せず原本として保存する。表示を試し、失敗時は代替表示と原本保存の操作を提供する」。自動JPEG変換と派生画像の生成は初期MVPに含めない。実機結果が出るまでは暫定採用案であり、全端末でHEICを閲覧できるとは約束しない。

ここでの原本は**選択後にWebアプリが受け取ったファイル**を指す。OS・ブラウザが選択時に変換した場合、撮影時のHEICそのものの保持は保証できない。表示・保存の可否と、変換前後の形式は別々に記録する。

## 文献で確認したこと

| 論点 | 確認内容 | 実測との区別 |
|---|---|---|
| HEICの表示 | WebKitはSafari 17でHEIC対応追加を告知している | 本プロジェクトのiPhoneで表示した結果ではない。OS・ブラウザ・ファイルの条件を実測する |
| 選択時の変換 | acceptは選択候補のヒントで、実際のファイル形式の保証やサーバー検証にはならない | 拡張子・File.type・ヘッダーを記録し、選択元・accept設定を変えて比較する |
| 共有による保存 | Web Share APIは安全なコンテキストと利用者の操作が必要。canShareでファイル共有を確認する | APIの完了は写真アプリへの保存成功を保証しない。保存先を手動確認する |

出典：

- [WebKit：Safari 17のHEIC対応](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/)
- [WHATWG：file inputとaccept](https://html.spec.whatwg.org/dev/input.html#file-upload-state-(type=file))

K01のIssue本文にあるAndroid・Chromeの非対応という記述は、全バージョン・全端末についての確定結果として使用しない。対象環境で確認する。

## 検証ページ

[検証ページ](k01/index.html)と[検証スクリプト](k01/probe.js)を用意した。外部ライブラリやSupabase接続は不要で、選んだ画像をサーバーへ送信しない。

- 端末・OS・ブラウザ、写真ライブラリ／ファイルの選択元、accept設定を記録する。
- File.name・File.type・バイト数・ヘッダーによる推定形式を表示する。ヘッダー推定は完全な画像検証ではない。
- JPEG・PNG・HEIC系・一般のHEIF系を区別する。HEIFコンテナだけではコーデックを断定せず、AVIFをHEICと誤認しない。
- ローカルの画像表示、1枚の共有、1枚のダウンロードを試す。保存先・選択前の原本形式・メモは手動入力する。
- JSONへ結果を出力する。ファイル名等を含むため、共有前に個人情報を確認する。
- 実投稿・署名URLによる表示はK02、複数枚共有・ZIPはA01で別途確認する。このページの成功をそれらの成功として扱わない。

### 開き方

PCでの準備確認はリポジトリ直下で以下を実行し、`http://localhost:8000/docs/k01/`を開く。

```powershell
python -m http.server 8000 --bind 127.0.0.1
```

スマホではこの端末自身のlocalhostを開いてもPCへ接続できない。チームのHTTPS検証環境へ **docs/k01/の2ファイルだけ** を配置し、そのURLで確認する。公開作業はこの変更に含まない。PCのLANアドレスをHTTPで開く方法ではWeb Share APIを適切に検証できない。

### 実機での手順

1. 元の形式が分かるJPEG・PNG・HEICを各数枚用意する。画像はリポジトリへ登録しない。
2. iPhoneのSafari／AndroidのChromeで機種・OS・ブラウザのバージョンを記録する。
3. 同じ写真を写真ライブラリとファイルから選ぶ。形式明示・image/*・JPEG/PNGのみのacceptで比較し、選択前と選択後を記録する。
4. 表示・共有・ダウンロードを試す。保存されたファイルの形式、保存先、再表示まで確認する。A01担当と同時に進める。
5. 結果JSONを保存し、以下の表へ反映する。ブラウザ内表示だけでなく、実投稿・署名URLの再検証をK02へ引き継ぐ。

## 容量評価

暫定で500MBを500,000,000 bytes（10進）とする。100枚を収めるには平均5,000,000 bytes以下が目安になる。これは計算値であり、実際の写真が収まるという検証結果ではない。

検証ページは選択後ファイルの件数・合計・平均・最大・平均×100を計算する。同じ写真を条件を変えて選んだ場合は重複するので、代表的な写真を重複なしで選び直して評価する。形式別・端末別に代表的な原本を各10枚程度集め、平均だけでなく最大値と混在時の合計も確認する。100枚未満でも先に500MBへ達したら追加を拒否する。

サーバーでの容量・枚数の保証はK05の担当とする。K02では形式・投稿・Storage登録を担当する。K01では制限の変更を確定せず、測定値を共有して合意する。

## 引き継ぐ仕様案

### 志鳥さん：T01のDB設計

- 写真に原本のStorageパス、選択後の検証済みMIME、バイト数、元ファイル名を保持する案とする。具体的な列名はT01で確定する。
- MVPでは表示用JPEGの生成を必須にしないため、表示用パスの専用列は必須にしない。将来変換を採用する場合は、nullableな派生画像パス・変換状態の追加migrationで対応する。
- 署名URLは期限付きの値なのでDBに恒久保存せず、K02で都度発行する。

### 佐藤さん：S03の表示

- 原本用の表示署名URLで画像表示を試し、読み込み失敗時は「この画像はこの端末では表示できません」等の代替表示を出す。
- HEICという形式名だけで非表示を決めない。URL失効・通信失敗も切り分け、期限内ならURL再取得後に再試行する。失敗したimgを無限に再読み込みしない。
- 保存の操作を残し、表示不可と保存不可を同一扱いしない。両OSで全画像の閲覧を必須にする場合は、変換処理の追加を別途合意する。

### 雨谷さん：A02の投稿／A01の保存

- 選択候補は`accept="image/jpeg,image/png,image/heic,image/heif,.jpg,.jpeg,.png,.heic,.heif"`を案とする。指定が変換に及ぼす影響は実機で比較する。
- File.typeが空または拡張子と食い違う可能性を考慮する。クライアントのacceptやMIMEだけで実形式を確定しない。
- 保存するのは受け取った原本。共有APIの可否を確認し、保存先・拡張子・再表示を手動確認する。複数枚／ZIPの採否はA01で決める。

### 斎藤さん：K02の投稿処理

- JPEG・PNG・静止画HEIC/HEIFの受入方針を実機結果後に確定し、未対応のシーケンス・不明なコーデックは明示的に扱う。一般のHEIFブランドだけでHEICと断定しない。
- サーバー側で実形式を検証し、不正形式を拒否する。拡張子・MIME・検証ページの簡易判定だけを信用しない。
- 署名URLの有効期限をルーム期限内に収め、変換処理を行わず原本を保管する。実投稿と署名URL表示はK02で確認する。
